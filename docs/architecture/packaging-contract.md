# Packaging contract

The checked package set now includes the Arch Linux `x86_64` template at `packaging/arch/PKGBUILD.in`, Docker-built Debian 12 and Ubuntu 24.04 packages under `packaging/debian/`, one distribution-aware RPM template at `packaging/rpm/fcitx-vinpst.spec.in` for Fedora 43 and openSUSE Leap 16.0, a bundled Linux tarball derived from the tested Ubuntu payload, and a locked source-build Nix flake. Arch, Debian/Ubuntu, Fedora/openSUSE RPM, and the bundled tarball are publication-shaped GitHub paths. Nix is published as a Cachix binary-cache channel rather than as a flat GitHub Release artifact.

## Package identity

The package is named `fcitx-vinpst`. It has no `Provides`, `Conflicts`, `Replaces`, or `Obsoletes` relationship with upstream or historical package identities. Package recipes install only Vinpst executables, addon metadata, D-Bus names, services, and XDG paths; they do not claim to replace or migrate another product.

Release-time native runtime selection is driven by the checked `packaging/arch/runtime-bundles.json` manifest and the shared strict loader in `scripts/release/runtime_bundles.py`. Arch, Debian, and RPM builds use the same schema, uniqueness, safe-token, architecture/Rust-target binding, archive-suffix, and lowercase SHA-256 checks. Each bundle binds one package architecture and Rust target to an exact sherpa-onnx archive/root/version, ONNX Runtime version, and digests for the runtime archive and both license files. The current production manifest contains only the validated `x86_64` sherpa-onnx 1.13.3 / ONNX Runtime 1.24.4 bundle. Nix instead source-builds sherpa-onnx from its locked flake input and links the locked nixpkgs ONNX Runtime. Adding another native bundle or architecture requires pinned inputs plus runtime-link validation and complete package smokes; silently falling back to an ABI-incompatible system runtime is not allowed.

## Runtime contents

The package builds `vinpst`, `vinpst-daemon`, and `vinpst-gui` in release mode; CLI/daemon enable both `pipewire-backend` and `sherpa-onnx-backend`. It installs:

- `/usr/bin/vinpst`, `/usr/bin/vinpst-daemon`, and `/usr/bin/vinpst-gui`;
- `/usr/lib/fcitx5/fcitx5-vinpst.so` and `/usr/share/fcitx5/addon/vinpst.conf`;
- `/usr/lib/systemd/user/vinpst-daemon.service` and `/usr/share/dbus-1/services/org.fcitx.Vinpst.service`;
- the default config reference under `/usr/share/fcitx-vinpst/default-config.json`;
- the Silero VAD model under `/usr/share/fcitx-vinpst/vad/silero_vad.onnx`;
- project, Silero VAD, sherpa-onnx, and ONNX Runtime license material.

No ASR language model is bundled. A fresh configured daemon therefore starts with an unavailable ASR backend instead of exiting or fabricating mock text; installing/selecting a model and reloading activates the real backend without replacing the package.

## Native runtime isolation

The package does not link against the independently packaged system sherpa-onnx runtime. It installs the exact sherpa-onnx C API and ONNX Runtime libraries used by the Rust crate under `/usr/lib/fcitx-vinpst`, then applies private relative rpaths:

- Rust binaries use `$ORIGIN/../lib/fcitx-vinpst`;
- `libsherpa-onnx-c-api.so` uses `$ORIGIN`.

The unused sherpa C++ API library is not installed. This boundary prevents a system sherpa or ONNX Runtime upgrade from silently changing the package ABI.

## Activation and configuration

The installed systemd user unit starts:

```text
/usr/bin/vinpst-daemon --dbus --configured-backends --audio-backend pipewire --exit-when-executable-replaced
```

The D-Bus activation file and the installed systemd user unit both start the daemon with `--exit-when-executable-replaced`. With configured backends and the packaged PipeWire recorder, ASR construction is fail-soft at startup: a missing or temporarily unusable active model installs an unavailable-backend placeholder, keeps the daemon idle and reachable over D-Bus, and records the backend error for diagnostics. A later model selection or configuration repair can therefore reload the real backend without requiring the service to have failed first. A later atomic package replacement changes the executable inode; the daemon detects the change, shuts down owned services, and exits unsuccessfully. A systemd-owned daemon is restarted immediately because the unit uses `Restart=on-failure` with a one-second delay. A daemon started directly by `dbus-daemon` is not supervised after exit, but the next D-Bus request activates the newly installed executable. The daemon discovers `$XDG_CONFIG_HOME/fcitx-vinpst/config.json` or `$HOME/.config/fcitx-vinpst/config.json`; the packaged reference config is not copied over user state during upgrades.

Staged CMake installs preserve their real runtime prefix and use `DESTDIR` as the filesystem staging root. A staging directory must never be passed as `cmake --install --prefix`: doing so changes generated runtime paths and can incorrectly move the absolute systemd user-unit directory under the temporary prefix. With the default `/usr/local` prefix, addon, locale, and D-Bus files stage under `DESTDIR/usr/local`, while the pkg-config-provided systemd unit remains under `DESTDIR/usr/lib/systemd/user`. The Arch recipe uses `/usr` plus `DESTDIR`, so all package files land under one `/usr` tree.

Package recipes may explicitly override the Fcitx module and systemd user-unit install directories. The CMake helper preserves those caller-provided values instead of replacing them with host pkg-config paths, normalizes relative and absolute destinations consistently, and does not create smoke executables when `BUILD_TESTING=OFF` or `VINPST_FCITX_BRIDGE_ENABLE_TESTS=OFF`. The RPM baseline therefore installs the addon under `/usr/lib64/fcitx5` and the unit under `/usr/lib/systemd/user` while normal CI still builds and runs the retained smoke targets.

## Package lifecycle hooks

Package-manager lifecycle hooks are deliberately non-mutating. Root package transactions must not discover desktop session buses, switch users, contact the Vinpst D-Bus service, stop/restart daemons, or run user-systemd commands. Arch `.INSTALL`, Debian maintainer scripts, and RPM scriptlets only print short guidance after install, upgrade, or removal. There is no package pre-remove hook.

Runtime transition remains owned by the normal daemon and desktop lifecycle. A running daemon already uses `--exit-when-executable-replaced`; a systemd-owned daemon is restarted by the unit policy after replacement, while a directly D-Bus-activated daemon is started from the new executable on the next request after the old process exits. Reloading Fcitx5 is left to the active desktop user. Explicit maintenance commands such as `vinpst daemon handoff` and `vinpst daemon prepare-remove` remain available for intentional user/admin troubleshooting, but package transactions never invoke them automatically.

Package removal preserves user config, models, and cache. It removes only package-owned files and does not attempt to mutate live user processes before those files disappear.

`scripts/release/render-arch-pkgbuild.py` loads the checked runtime-bundle manifest, selects its declared default or the explicit `--runtime-bundle`, validates the schema, unique identifiers, shell-safe fields, architecture/Rust-target binding, and every digest before writing output, then copies the checked install script beside the rendered PKGBUILD. Generated release directories are therefore complete makepkg inputs rather than a PKGBUILD that silently depends on files left in the source tree.

## Reproducibility and validation

The template pins source archives and third-party license checksums. Arch makepkg LTO is disabled because linker-plugin LTO breaks the `ring` build script's C/assembly objects; normal Rust release optimization remains enabled. Debug splitting is disabled for the already stripped release artifacts.

Development/test builds may resolve the repository VAD asset through a build-script-provided path. Release builds do not embed that source-tree path and resolve only explicit, user XDG, or system XDG VAD locations.

The following gates cover the recipe:

- `scripts/release/check-arch-install-script.sh` syntax-checks the lifecycle hooks, executes each hook with an intentionally empty `PATH`, requires concise stdout-only guidance, and proves there is no pre-remove hook. It is part of `just ci`.
- `scripts/release/check-arch-pkgbuild.sh` renders the default runtime bundle, parses it with `makepkg --printsrcinfo`, and verifies identity, dependencies, the absence of unintended replacement metadata, architecture, Rust target, source URLs, options, and pinned checksums. Fixture manifests prove explicit cross-architecture/version selection and reject unknown bundles, duplicate IDs, malformed digests, and unsafe tokens before a PKGBUILD is written. It is part of `just ci`.
- `scripts/release/check-rpm-spec.sh` renders the RPM template through the same runtime-bundle loader, parses it with `rpmspec`, verifies identity, architecture, dependency policy, the absence of unintended replacement metadata, product-only CMake targeting, hint-only lifecycle scriptlets, and unresolved-placeholder rejection, and proves invalid release/source/digest/bundle inputs fail before output is published. It is part of `just ci`.
- `scripts/release/check-deb-package.sh` validates Debian metadata, hint-only maintainer scripts, runtime dependencies, GPL copyright metadata, invalid renderer inputs, and unresolved placeholders. `scripts/release/run-deb-package-smoke.sh` builds release 1 and synthetic release 2 in Debian 12 and Ubuntu 24.04 Docker images, validates payload/linkage/rpaths/GUI behavior, then performs real `dpkg` install, upgrade, verification, removal, and purge while preserving unsupported-future user config byte-for-byte.
- `scripts/release/check-nix-flake.sh` validates the lock-file schema, root input references, non-root pinning metadata, and GitHub input revisions without asserting `flake.nix` implementation text or installation layout. `scripts/release/run-nix-package-smoke.sh` is the release-grade package contract: it evaluates the locked flake without updating it, runs `nix flake check`, builds the closure, executes the CLI/daemon and offline GUI binary/config self-check, and verifies the addon, activation metadata, desktop assets, model assets, translations, and project license. The headless GUI command is packaging evidence, not GUI-interaction evidence.
- `scripts/release/check-source-archive.sh` proves the shared source archive is deterministic, includes only tracked or non-ignored regular files for dirty local candidates, and excludes VCS/build/cache/generated state. The checked extractor accepts only a regular gzip tar with one versioned Vinpst root, regular files/directories, unique normalized paths, and required Cargo metadata; it rejects archive symlinks, path traversal, foreign roots, unsupported members, and destination replacement.
- `just package-smoke` performs a clean `makepkg` build, verifies the package archive carries the checked `.INSTALL` lifecycle hooks, extracts the package, validates the complete file set, private rpaths and dynamic linkage, confirms no build-tree path remains, runs the packaged CLI, daemon, and Rust GUI binaries, checks the GUI desktop/icon assets and display-independent `vinpst-gui --check --offline`, and verifies systemd/D-Bus activation commands. It then uses `makepkg --repackage` to create a `pkgrel=2` archive without recompiling and invokes the direct transaction, local repository, signed repository, and release-artifact bundle smokes. It is an explicit release gate because it downloads fixed upstream assets and recompiles release binaries.
- `scripts/release/run-arch-package-transaction-smoke.sh` reuses the `pkgrel=1` and `pkgrel=2` archives under a fakeroot-isolated pacman root. It proves package database registration, file ownership and integrity, install, upgrade, same-source `pkgrel=2` to `pkgrel=1` rollback, and removal. A pre-existing version-2 user config remains byte-identical throughout; the package-installed CLI rejects that unsupported future schema after initial install, upgrade, and rollback with nonzero status and no JSON stdout. The retained SHA-256 is rechecked after removal, and the package owns no `/etc` or `/home` paths. This proves refusal and preservation of unknown future state, not rollback of a future schema migration that does not yet exist.
- `scripts/release/run-arch-repository-smoke.sh` creates a local `repo-add` database containing `pkgrel=1`, synchronizes it through a `file://` pacman repository, and installs the package with `pacman -S`. It then replaces the repository entry with `pkgrel=2`, refreshes the sync database, upgrades through the repository, verifies both downloaded package archives reached pacman's cache, checks package integrity and user-config preservation, and removes the package. The repository intentionally uses `SigLevel = Never`; signing and trust policy remain external-publication work.
- `scripts/release/run-arch-signing-smoke.sh` generates an ephemeral Ed25519 signing key under `target/tmp`, signs both package archives and the `repo-add` database, imports only the public key into a user-owned isolated GnuPG keyring with explicit ownertrust, and requires `SigLevel = Required DatabaseRequired`. Only the synthetic pacman installation roots use fakeroot. The gate prepares short per-keyring runtime sockets when `XDG_RUNTIME_DIR` is available, so nested CI source paths cannot exceed Unix-domain socket limits. It proves signed install and upgrade, verifies pacman reports `SHA-256 Sum  Signature`, rejects the signed database when the signer is absent from another isolated keyring, and rejects a same-size byte-flipped package as an invalid PGP signature. No private key, fingerprint, or trust database is checked into the repository. Production key custody, rotation, revocation, and public-key distribution remain release-operations work.

## Fedora and openSUSE RPM release paths

`just rpm-package-smoke` creates a clean source archive by default, while the release workflow supplies the already checked source archive produced by its source job. The gate checksum-verifies that archive plus the pinned native runtime and license files, renders release `1` and release `2`, and builds both with `rpmbuild`. The package contains the same CLI, daemon, Rust GUI, Fcitx addon, activation metadata, translations, VAD asset, and private sherpa/ONNX Runtime libraries as the Arch package, with `/usr/lib64/fcitx5` for the addon and `/usr/lib/systemd/user` for the unit. The gate verifies unsigned-package digests in an isolated rpmdb, package metadata and hint-only scriptlets, exact payload inventory, absence of build-tree paths, private rpaths and dynamic linkage, packaged binary execution, desktop/activation commands, and `vinpst-gui --check --offline`.

The same gate then uses an unprivileged user namespace to give RPM a real isolated chroot and rpmdb. It performs `--noscripts` install, release-1 to release-2 upgrade, package verification, and removal, and proves a pre-existing unsupported-future-schema user config remains byte-identical and unowned throughout. The release workflow runs this complete gate independently inside Fedora 43 and openSUSE Leap 16.0, with distro-specific BuildRequires rendering and a shared portable runtime dependency boundary; each job publishes only release `1`, while release `2` remains synthetic upgrade evidence. Private sherpa/ONNX Runtime libraries are excluded from RPM automatic provides/requires. Scriptlets are not executed inside the synthetic rpm root because it intentionally lacks a live desktop session, so real desktop lifecycle-script execution remains separate evidence. Hosted DNF/Zypper repositories, package/repository signing, and SELinux policy review remain follow-on distribution work.

## Debian and Nix release paths

The Debian builder creates distribution-labelled `amd64` packages for Debian 12 and Ubuntu 24.04. Both carry multiarch Fcitx addon placement, the checked private native runtime, hint-only maintainer scripts, desktop integration, project/third-party licenses, and runtime dependencies needed by the product itself rather than cross-user package dispatch. The Docker matrix installs release 1, upgrades to release 2, runs `dpkg -V`, removes and purges the package, and verifies user configuration remains unowned and unchanged. In the tag workflow, each matrix job extracts and builds from the single source artifact produced by `source-archive`; it does not package the independent Actions checkout. Release 2 is test-only and is explicitly excluded from publication selection.

The Nix flake builds `x86_64-linux` and declares `aarch64-linux`, using immutable store paths rather than package-manager lifecycle scripts. Its lock file pins nixpkgs and the sherpa-onnx flake. Routine CI checks the lock metadata semantically, while the full package smoke passes `--no-update-lock-file` during metadata evaluation, `nix flake check`, and the build itself. The closure contains the Rust binaries, Fcitx addon, activation metadata, desktop assets, models, translations, and licenses. The release job extracts the same checked source archive used by the native packages, runs the complete locked Nix package smoke once, and publishes the resulting `x86_64-linux` closure to the public `fcitx-vinpst` Cachix cache using a repository-scoped write token. Cache reads are public; the Cachix substituter and managed public key are added to the flake only after the cache exists and the exact key can be pinned. Additional architectures and long-term cache retention policy remain follow-on work.

## Flatpak boundary

The Rust CLI detects `/.flatpak-info`, routes host service/log/signal commands through `flatpak-spawn --host`, reports the required `pipewire`, `xdg-config/systemd`, and `xdg-cache` grants, and can render/install the legacy-compatible host user unit through `vinpst daemon install-service`. Unit generation preserves the packaged daemon arguments, rewrites `ExecStart` to the configured Flatpak application/addon path, adds `ExecStop`, writes atomically, and reloads the host user manager. Unit tests and CLI process tests cover permission parsing, dry-run rendering, real atomic write, and daemon-reload argv.

The checked Flatpak baseline is an `org.fcitx.Fcitx5.Addon.Vinpst` extension rooted at `/app/addons/Vinpst`. Its renderer combines the fixed KDE/Fcitx/Rust/LLVM runtime contract, Cargo.lock-derived crates.io sources, the shared native-runtime manifest, and a deterministic project source archive. The outer gate prefetches the Sherpa archive and third-party licenses with bounded transport, verifies their shared-manifest SHA-256 values, and passes only local relative sources to Flatpak Builder. It accepts an explicit source archive for release assembly; the tag workflow copies the exact source-job artifact bytes into the build tree, records their SHA-256, and verifies that digest again before selecting the publication bundle. The Docker transaction then builds the Rust CLI, daemon, GUI, and C++ addon once; exports an OSTree repository; installs revision 1; runs packaged version and display-independent GUI binary/config checks through the Fcitx host application; creates the publication bundle from that exact commit; applies a marker-only synthetic revision 2 through a real Flatpak update; removes the extension; reinstalls the revision-1 bundle; and removes it again. The summary proves the publication bundle commit equals revision 1 and differs from the synthetic update commit; these headless checks are packaging evidence rather than GUI-interaction evidence.

This is a distributable, transaction-tested x86_64 package baseline, but not yet complete production Flatpak support. A real desktop-session gate still needs to prove Fcitx discovers and loads the extension, PipeWire recording works through the declared permissions, the generated host user service survives install/upgrade/removal, and GUI interaction works under Wayland/X11. Production repository signing, Flathub submission/update policy, runtime-branch maintenance, and unrelated-machine validation also remain.

## Release artifact inventory

`scripts/release/release_manifest.py` assembles a flat release-artifact directory through a temporary sibling and verifies it before publication. `manifest.json` uses an exact schema: package name/version/architecture, one unique role per artifact, byte size, and lowercase SHA-256. `SHA256SUMS` is sorted by artifact name and must exactly match the manifest. The verifier rejects duplicate roles or basenames, unsafe names, symlinks, nested directories, non-regular entries, missing files, digest/size changes, and any unlisted extra file.

The tag workflow publishes one deterministic source archive, one deterministic bundled Linux x86_64 tarball, the Arch Linux x86_64 `pkgrel=1` package, the Debian 12 and Ubuntu 24.04 release-1 packages, Fedora 43 and openSUSE Leap 16.0 x86_64 RPM release-1 packages, and the revision-1 x86_64 Flatpak extension bundle through this checked release directory. Arch, Debian, both RPM jobs, and Flatpak consume the exact source-job archive; the bundled tarball reuses the already transaction-tested Ubuntu release-1 `/usr` payload and normalizes its tar/gzip metadata rather than recompiling. The tarball bundles the private sherpa-onnx/ONNX Runtime libraries but intentionally relies on ordinary compatible host libraries and desktop services; its release job therefore satisfies the formal Ubuntu package's declared `Depends` before executing the extracted CLI/daemon/GUI self-checks. Arch, both RPM jobs, and Flatpak record and recheck the consumed archive digest before publication selection. The same release DAG separately builds the locked Nix closure from that extracted source and publishes it to Cachix; Nix is therefore a required release channel but not a file role in the flat GitHub bundle. The bundle additionally depends on the same reusable CI workflow used for pull requests, which contains strict MkDocs plus the complete deterministic Rust/FFI/integration checks but no release-grade package build. Ordinary CI keeps only lightweight package metadata and contract checks through `just ci`, including semantic Nix lock validation; full native package construction and the full Nix closure smoke remain Release boundaries operating on the exact checked source archive. Synthetic Arch `pkgrel=2`, Debian/RPM release-2, temporary package/repository signatures, temporary public keys, and the synthetic Flatpak revision-2 commit remain only inside their transaction gates. Production Arch/RPM repository publication and signing, production Flatpak repository/signing operations, detached production manifest signing, and production signing-key custody remain explicit follow-on release operations.

`--force` is deliberately narrow: it may replace only an existing bundle that already passes the same verifier. It cannot recursively delete an arbitrary directory, and an input artifact inside the output directory is rejected before any replacement. Assembly occurs in a new temporary directory so a copy, serialization, or validation error never publishes a partial bundle.

`scripts/release/check-release-manifest.sh` is the lightweight deterministic gate in `just ci`. It exercises successful assembly/verification and negative extra-file, same-size mutation, symlink, nested-directory, schema-drift, unsafe-force, in-output-source, and duplicate-role cases with tiny fixtures.

`manifest.json.sig` is optional metadata rather than a manifest artifact. Excluding the detached signature from `manifest.json` and `SHA256SUMS` avoids a recursive digest/signature dependency while retaining strict inventory checks: if the file is present it must be a regular top-level file with the reserved name, and rebuilding a bundle replaces the old directory without carrying a stale signature forward.

`scripts/release/sign-release-manifest.sh` accepts an already verified bundle, a caller-supplied GPG home, and an exact primary fingerprint. It requires the matching secret key, writes the detached signature to a sibling temporary file, verifies that temporary signature, publishes it atomically as mode `0644`, and never exports key material. `scripts/release/verify-release-bundle-signature.sh` requires a public-key file from outside the bundle plus the independently pinned fingerprint. It imports exactly one primary key into a temporary isolated GPG home, disables automatic key retrieval, requires a matching `VALIDSIG`, and only then runs the full artifact/checksum verifier. It never trusts a key merely because the same bundle contains a copy.

`scripts/release/check-release-signature.sh` is the lightweight deterministic signature gate in `just ci`. It proves signing, explicit re-signing, external-key verification, and the unsigned-after-rebuild boundary. It rejects a missing or modified signature, modified manifest, modified artifact, wrong key, wrong fingerprint, bundled-key trust, and an unavailable secret key. All generated keys live only under `target/tmp`.

`scripts/release/run-arch-release-bundle-smoke.sh` is part of the complete Arch release gate. After package and repository signing, it assembles exactly 13 release-gate artifacts: the source archive, rendered `PKGBUILD`, `.SRCINFO`, lifecycle script, `pkgrel=1` package/signature, synthetic `pkgrel=2` package/signature, signed repository database/files archives and signatures, and the ephemeral public key. It rechecks `SHA256SUMS`, verifies all four artifact signatures, signs `manifest.json` with the ephemeral release-gate key, verifies that signature using the public key outside the bundle and its pinned fingerprint, and proves extra, artifact-mutated, and signature-mutated bundle copies are rejected.

The roles `package-pkgrel2-test`, `package-signature-pkgrel2-test`, and `signing-public-key-test` explicitly mark test-only evidence. This directory is a release-gate bundle, not a public release set. The detached-manifest signing mechanism is deterministic, while publication selects only actual release artifacts and excludes ephemeral test assets.

## Release promotion

`scripts/release/prepare-arch-release-candidate.sh` is the explicit promotion boundary between the broad release-gate evidence bundle and a publication-shaped candidate. It first verifies the gate's detached manifest signature against the external public key and pinned fingerprint, then requires the exact 13-role gate policy. It selects only `package-pkgrel1` and its signature, rebuilds fresh `repo-add` database/files metadata containing that package alone, signs those repository indexes with the caller-supplied signing home, copies the external public key under a stable name, assembles a new bundle, signs its manifest, and invokes the candidate verifier before reporting success. The repository builder supports both pacman 6, which automatically embeds a sibling package signature, and pacman 7, which requires the explicit `--include-sigs` option; both paths still sign the database/files indexes and are subject to the same candidate verification.

The candidate uses exactly 11 production roles: source archive, rendered Arch metadata, lifecycle script, package/signature, repository database/files archives and signatures, and signing public key. Role and file names containing `test` or `synthetic` are rejected. The candidate verifier checks the package name/base version/pkgrel/architecture, all three artifact signatures, the exact external public-key bytes, and the single repository entry's name/version/architecture/filename. It therefore prevents the synthetic `pkgrel=2` upgrade fixture or its repository metadata from leaking into a publication candidate.

Existing output is never replaced implicitly. `--force` first verifies the old candidate cryptographically and structurally; arbitrary directories, invalid candidates, symlink outputs, and descendants of the signed gate are refused. The lightweight `scripts/release/check-arch-release-candidate.sh` builds minimal packages, a signed synthetic gate, and a promoted candidate entirely under `target/tmp`, then proves normal promotion, safe force replacement, gate-as-candidate rejection, output-path protection, invalid-force preservation, and mutation rejection.

The complete Arch gate promotes the real package outputs after all signing checks. Because that test still uses an ephemeral key, its candidate under `target/tmp` is not itself a public release. A production invocation must supply the managed signing home plus independently distributed public key and fingerprint, then publish only the verified candidate directory.

The current recipe proves package construction, extracted-runtime behavior, isolated pacman install/upgrade/same-version-rollback/uninstall transactions, local repository metadata/install/upgrade behavior, ephemeral signed-repository trust/tamper enforcement, strict release-gate artifact inventory/checksums, detached manifest signing against an external pinned key, test-role-free release promotion with rebuilt repository metadata, and non-mutating lifecycle guidance at each package transition. `vinpst daemon status` still detects a running D-Bus owner from a different executable path or an executable inode unlinked by package replacement, and the explicit `vinpst daemon handoff` command retains its guarded systemd/direct-owner recovery behavior for intentional use. Package hooks do not call that command. Rust behavior tests prove same-inode startup identity, atomic executable replacement detection, and asynchronous watcher completion. CLI, CMake staging, addon-install, and package checks prove that both direct D-Bus activation metadata and the systemd unit pass the watcher flag, while the unit additionally enables failure restart. `run-direct-activation-upgrade-smoke.sh` proves direct-owner exit and next-request reactivation against a private session bus; `run-daemon-handoff-smoke.sh` separately proves explicit current-owner no-op, busy-systemd refusal, stale-systemd restart, stale-direct replacement, and guard/control-failure preservation. The opt-in `scripts/live/system/run-systemd-upgrade-live.sh` gate proves the systemd-owned executable-replacement path at process level without making package installation responsible for session mutation.

Package removal has no daemon handoff or pre-remove lifecycle mutation. The package manager removes package-owned activation metadata and binaries and leaves any user-session cleanup to the normal process lifecycle or an explicit maintenance command. `scripts/tests/daemon/run-daemon-removal-handoff-smoke.sh` remains evidence for the manual `vinpst daemon prepare-remove` command only; it is not a package-transaction contract. The current config schema is accepted only at its exact published version; unsupported versions are rejected before use, and package transactions never rewrite user config. An actual host package-installed upgrade, externally hosted repository publication, production signing-key custody/rotation/revocation, independent fingerprint/public-key distribution, and external-user live validation remain separate operational validation work. Rollback of a real schema migration becomes a release requirement only when a second production schema is introduced.
